# Photo Selection Submitted — automatic WhatsApp notification: audit and design

Date: 2026-10-20. Builds on `2026-10-17-whatsapp-activity-log-design.md`.

## Audit

- **Where a client's submission is persisted.** `POST /api/public/image-selection/galleries/:token/submit-selection` → `publication/service.js` `submitSelection` → `repository.markSubmitted` (one transaction: stamps each selection item's `selectionSubmittedAt` and, once none is open, the publication's; the publication row is locked first so two submits run one after the other; an item already stamped makes the whole write roll back with 409). A gallery with no selection items takes the older path, `markSelectionSubmitted`. Selecting or deselecting photos goes through different routes and never touches these.
- **Group delivery that exists.** Only the paired-phone sessions (Baileys) can write to a WhatsApp group; the Meta Cloud API path sends template messages to one number and is not used for groups. The attendance report and the wishes both send through `hrm/attendance/reportGroup.deliverToGroup(target, body, …)`: Priority 1 (a chosen login with Allow WhatsApp), then every other Allow-WhatsApp employee in order, each matched against **their own** WhatsApp groups by name at send time (`groupMatching`), both chat switches honoured, an ambiguous failure stopping the try ("maybe-sent") rather than sending twice. That is the supported, explicitly configured mechanism; this feature reuses it unchanged.
- **Where the attendance and wishes configuration lives.** Columns on the one `hrm_settings` row (`SETTINGS_ID`): group name, send time, Priority 1 (`*_sender_user_id` → `user`), last attempt, last error. The wishes scheduler (`settings/wishes/scheduler.js`) is the second configuration on the same row; its Settings panel is `AttendanceWhatsAppReportPanel` with its own `api` and `wording`.
- **Templates.** `message_template` rows keyed by `TEMPLATE_KEYS`, rendered by `services/messageTemplate.js` with `{placeholder}` (single braces, case- and space-insensitive), edited in Settings → Templates → Message Template (`MessageTemplatePanel`, one template per `templateKey`, behind `SETTINGS / Message Template`). Seeded by migration with `INSERT … WHERE NOT EXISTS`.
- **Activity log.** `services/whatsappActivity.js` `track(context, sendFn)`; `deliverToGroup` already takes an `activity` context and records each try (and a try nobody could make) against one `logicalKey`. Resend from the log works for a GROUP row that carries a sender and a group id.
- **Queues.** BullMQ serves the Meta path only; the paired sockets live in the API process, so every group send runs there - the attendance report and wishes on an in-process timer with a claim and a retry gap. A durable queue for this feature is therefore the activity row itself (`QUEUED` in the database), worked by an in-process loop of the same shape.

## Design

- **Settings → User Settings → Automatic WhatsApp Message → Photo Selection Submitted**, behind a new permission `SETTINGS / Automatic WhatsApp Message` (`SETTINGS_AUTOMATIC_WHATSAPP`, SUPER_ADMIN only by migration). The panel is `AttendanceWhatsAppReportPanel` with its own `api`/`wording` (no daily time), plus an **Enabled** toggle and the template editor (`MessageTemplatePanel` for key `PHOTO_SELECTION_SUBMITTED`, which saves through the Message Template endpoint and so also needs `SETTINGS / Message Template` Read / Write, as Table Settings needs CRM Leads).
- **Configuration** on `hrm_settings`: `photo_selection_notify_enabled` (false), `photo_selection_group_name`, `photo_selection_sender_user_id` → `user`, `photo_selection_last_error`. Attendance and wishes columns are untouched.
- **Template** `PHOTO_SELECTION_SUBMITTED`, seeded by migration, placeholders `{client name}`, `{project name}`, `{event name}`, `{selected count}`, `{submitted at}` (the app's `{…}` convention, not `{{…}}`). A missing value renders as "—"/"the project", never `undefined`.
- **Trigger.** After `markSubmitted`/`markSelectionSubmitted` resolve (the transaction committed), `submitSelection` calls `photoSelection.afterSubmission({ projectId, submittedIds })` fire-and-forget: it reads the configuration, and when enabled with a group named, writes one `whatsapp_activity` row `QUEUED` with `logical_key = isel-selection-submitted:<projectId>:<sorted item ids | all>` (idempotent: a second call for the same key does nothing) and asks the loop to run. Nothing about the response or the client's saved selection depends on it; a failure to enqueue is logged.
- **Sending loop** (`startPhotoSelectionNotifier`, every minute, in the API process, off with `PHOTO_SELECTION_NOTIFY_AUTOSEND=false`): takes `QUEUED` rows, and `FAILED` rows younger than 2 hours with fewer than 3 tries whose last try is 5 minutes old and was not ambiguous, claims each (conditional update to PROCESSING), renders the template from the project, and sends through `deliverToGroup` with the row's own activity context - so the try, the sender, the group id and the outcome land on that row. An ambiguous try leaves the row FAILED and unretried by the loop; the Activity Log's Resend asks for confirmation. `photo_selection_last_error` keeps the last reason for the panel.
- **Activity log.** Trigger `PHOTO_SELECTION_SUBMITTED`, module Image Selection, mode AUTOMATIC, links `imageSelectionProjectId` and `salesProjectId`, template key, rendered body, resendable once a sender and group were found.
